### 2.2. Формалізація нефункціональних вимог (`requirements.md`, §6)
Кожну нефункціональну вимогу переведено у вимірюваний формат із конкретними числами, верхніми/нижніми межами та умовами вимірювання:
1. **Пристрої та ОС за ролями:**
   - **Клієнт / Гість:** смартфони `iOS 16+` та `Android 11+` (застосунок або мобільний браузер Chrome/Safari останніх 2 версій), діагональ `4.7"–6.9"`, ширина viewport `360px–430px`.
   - **Офіціант:** робочий планшет `iPadOS 16+` або `Android 12+`, діагональ `8"–11"` (`≥ 1280×800`), локальна мережа Wi-Fi 5/6.
   - **Адміністратор:** планшет або ПК/ноутбук з діагоналлю `10"–24"` (`1024×768` – `1920×1080`), вебінтерфейс у Chrome / Edge / Safari останніх 2 мажорних версій.
   - **Кухар:** сенсорний екран `Kitchen Display System (KDS)` `15"–27"`, роздільна здатність `1920×1080 (Full HD)`, ОС `Android 12+ / Linux (Chromium Kiosk mode)`.
2. **Час відгуку та умови (профілі) вимірювання:**
   - Первинне відмальовування меню (LCP): `p95 ≤ 1.5 с, p99 ≤ 2.2 с` (мережа 4G ≥ 10 Мбіт/с, RTT ≤ 50 мс, профіль: каталог до 100 страв при 150 одночасних сесіях).
   - Перерахунок вартості чека: `p95 ≤ 200 мс, p99 ≤ 350 мс` (профіль: 50 RPS при 200 активних сесіях, кошик до 20 позицій).
   - Доставка сповіщень з кухні офіціанту: `p95 ≤ 1.0 с, p99 ≤ 1.8 с` (при піковому навантаженні 50 активних замовлень у залі).
   - Синхронізація статусів столів через WebSocket: `p95 ≤ 500 мс`.
   - Пошук страви в інтерфейсі офіціанта: `p95 ≤ 150 мс`, розмір tap-елементів `≥ 48×48 px`.
   - Відображення та оновлення черги на KDS: до `75 активних замовлень` при `≥ 60 FPS` і затримці оновлення `p95 ≤ 300 мс`; звукове оповіщення про скасування — `≥ 70 дБ` тривалістю `3 с` із затримкою `p95 ≤ 500 мс`.
3. **Навантаження та поведінка понад межу (Overload behavior):**
   - **Штатне (очікуване):** `150 одночасних сесій`, `15 нових замовлень/хв` (~50 RPS).
   - **Пікове:** до `500 одночасних сесій`, до `50 нових замовлень/хв` (~200 RPS) із часом відгуку читання `p95 ≤ 250 мс` і запису `p95 ≤ 400 мс`.
   - **Понад межу (> 500 сесій або > 200 RPS):** спрацьовує Rate Limiter зі статусом `HTTP 429 Too Many Requests` та заголовком `Retry-After: 5` (запити оплати й кухні обробляються через пріоритетну чергу без втрати даних).
4. **Безпека, локалізація та технологічний стек:**
   - Шифрування трафіку `TLS 1.3`, делегування карткових платежів шлюзу `PCI DSS Level 1` (без збереження PAN/CVV у БД), `OAuth 2.0 / JWT` (`access TTL = 15 хв`, `refresh TTL = 7 діб`), `bcrypt (cost factor ≥ 12)`, блокування акаунту на `15 хв` після `5 невдалих спроб` входу, зберігання audit-логу `≥ 365 діб`.
   - Захист від овербукінгу: транзакції з рівнем ізоляції `SERIALIZABLE` / `SELECT ... FOR UPDATE` (таймаут `≤ 2 с`, `0%` колізій).
   - Мови: українська та англійська як основні (додатково DE, FR, ES), автовизначення за `Accept-Language`, перемикання за `p95 ≤ 100 мс`.
   - Стек: `React Native (TypeScript)` для мобільного застосунку та планшета офіціанта, `Vue 3 (TypeScript)` для вебпанелі адміністратора та KDS, `Python 3.12 + FastAPI`, `PostgreSQL 16`, `Redis 7`.

## 3. Прийняті рішення (Accepted Decisions)

| № | Рішення | Обґрунтування |
| :--- | :--- | :--- |
| **AD-1** | Обрати `UC1_1` («Забронювати стіл») як єдиний прецедент глибокої деталізації | Для нього вже сформовано `US1.1` із детальними критеріями приймання та 4 різнопланові Gherkin-сценарії (автовибір, ручний вибір, відсутність місць, ліміт >3 столів), що ідеально демонструє перехід «Сценарії → EARS (`REQ1`–`REQ4`)». |
| **AD-2** | Вимірювати латентність через перцентилі `p95` та `p99` із прив'язкою до профілю навантаження | Середній час відгуку не показує деградацію системи в пікові години роботи ресторану; перцентилі `p95`/`p99` при конкретному RPS і кількості сесій роблять вимогу перевірюваною під час навантажувального тестування. |
| **AD-3** | Розділити клієнтський фронтенд-стек на `React Native` (мобільні пристрої) та `Vue 3` (KDS та панель адміна) | Замість невизначеного запису «react native or vue» чітко розмежовано платформи: мобільним ролям (`CLIENT`, `WAITER`) потрібні нативні можливості та Push-сповіщення (`React Native`), а широкоформатним екранам (`ADMIN`, `CHEF KDS`) — реактивний SPA-інтерфейс у браузері/кіоску (`Vue 3`). |
| **AD-4** | Застосувати `HTTP 429 Too Many Requests` з `Retry-After: 5` та пріоритизацією черг при перевантаженні (>500 сесій) | Дозволяє захистити БД від каскадного падіння під час пікового напливу відвідувачів, гарантуючи при цьому безперебійне проведення оплат і передачу замовлень на кухню. |
| **AD-5** | Пояснити відсутність окремих таблиць оплати, сповіщень і статистики в ER-моделі Lab1 через архітектурний розподіл | Карткові дані делегуються зовнішньому PCI DSS шлюзу (у БД зберігається лише статус `ORDER.status = COMPLETED`), сповіщення є stateless-подіями через Redis Pub/Sub, а статистика агрегується SQL-запитами з `ORDER` та `MENU_ITEM`. |

## 4. Відхилені рішення та альтернативи (Rejected Decisions)

| № | Відхилена ідея / початковий варіант | Причина відхилення |
| :--- | :--- | :--- |
| **RD-1** | Залишити якісні оцінки в NFR (*«одразу перераховується»*, *«приблизно p95»*, *«швидко доставляється»*, *«коректно адаптується»*) | Відхилено як нетестовані формулювання. Вимога без точних числових меж і профілю вимірювання не може бути об'єктивно перевірена (порушує критерій однозначності NFR). |
| **RD-2** | Додати NFR на діаграми Use Case та в матрицю трасування (§5) | Відхилено згідно з методологією UML та вимогами завдання: NFR є наскрізними обмеженнями якості системи в цілому (або окремих інтерфейсів), а не функціональними прецедентами використання. |
| **RD-3** | Вважати `Платіжний шлюз` та `Notification Service` повноцінними акторами, що ініціюють Use Cases | Відхилено в специфікації (`spec.md`): ці зовнішні сервіси не мають власної бізнес-мети в системі TableFlow і ніколи самі не ініціюють прецедент — вони викликаються системою як деталі реалізації інтеграцій. |
| **RD-4** | Зберігати реквізити банківських карток (PAN/CVV) у власній базі даних для підсистеми оплати | Відхилено з міркувань безпеки: це вимагало б дорогої сертифікації всієї інфраструктури ресторану за стандартом PCI DSS. Обрано токенізований редірект/віджет платіжного шлюзу. |
| **RD-5** | Деталізувати всі 27 вимог (`REQ1`–`REQ27`) як рівнозначні основні Use Cases у `spec.md` | Відхилено, оскільки це розмиває фокус специфікації. Вимоги `REQ5`–`REQ27` залишено як оглядову функціональність («Поза обсягом глибокої деталізації»), а фокус зосереджено на `UC1_1`. |

## 5. Власні зауваження автора до звіту AI та план подальших дій

1. **Верифікація чисел у NFR:** запропоновані показники (`150` штатних / `500` пікових сесій, `50` замовлень/хв, затримка `p95 ≤ 200 мс` для перерахунку кошика) перевірено автором на реалістичність для середнього/великого ресторану (50–80 столів) із бекендом на FastAPI + PostgreSQL + Redis.
2. **Виправлення застарілого посилання в `AI/comments.md`:** у попередньому звіті AI (`AI/comments.md`, рядок 143) згадувалася проміжна таблиця `TABLE_RESERVATION`, тоді як у фінальній ER-діаграмі `Lab1/models/base_model.mmd` використовується прямий зв'язок `RESERVATION }o--|{ TABLE`. У актуальній документації (`spec.md`, `DEFENSE.md`) використовується виключно сутність `RESERVATION`.
3. **Наступні кроки (технічний борг по моделях та сценаріях):**
   - Очистити підсистемні `.mmd` діаграми від дублікатів акторів, неоголошених вузлів (`UC1`..`UC6` у `pay_system.mmd`) та системних кроків, які не є самостійними потребами акторів.
   - Виправити параметризацію `Scenario Outline` та таблицю `Examples` у `features/pay_system.feature`.
