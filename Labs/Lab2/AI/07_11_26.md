### 2.2. Формалізація нефункціональних вимог (`requirements.md`, §6)
Кожну нефункціональну вимогу переведено у вимірюваний формат із конкретними числами, верхніми/нижніми межами та умовами вимірювання:
1. **Пристрої та ОС за ролями:**
   - **Клієнт / Гість:** смартфони `iOS 16+` та `Android 11+` (застосунок або мобільний браузер Chrome/Safari останніх 2 версій), діагональ `4.7"–6.9"`, ширина viewport `360px–430px`.
   - **Офіціант:** робочий планшет `iPadOS 16+` або `Android 12+`, діагональ `8"–11"` (`≥ 1280×800`), локальна мережа Wi-Fi 5/6.
   - **Адміністратор:** планшет або ПК/ноутбук з діагоналлю `10"–24"` (`1024×768` – `1920×1080`), вебінтерфейс у Chrome / Edge / Safari останніх 2 мажорних версій.
   - **Кухар:** сенсорний екран `Kitchen Display System (KDS)` `15"–27"`, роздільна здатність `1920×1080 (Full HD)`, ОС `Android 12+ / Linux (Chromium Kiosk mode)`.
2. **Час відгуку та умови (профілі) вимірювання:**
   - Первинне відмальовування меню (LCP): `p95 ≤ 1.5 с, p99 ≤ 2.2 с` (мережа 4G ≥ 10 Мбіт/с, RTT ≤ 50 мс, профіль: каталог до 100 страв при 150 одночасних сесіях).
   - Перерахунок вартості чека: `p95 ≤ 200 мс, p99 ≤ 350 мс` (профіль: 50 RPS при 200 активних сесіях, кошик до 20 позицій).
   - Доставка сповіщень з кухні офіціанту: `p95 ≤ 1.0 с, p99 ≤ 1.8 с` (при піковому навантаженні 50 активних замовлень у залі).
   - Синхронізація статусів столів через WebSocket: `p95 ≤ 500 мс`.
   - Пошук страви в інтерфейсі офіціанта: `p95 ≤ 150 мс`, розмір tap-елементів `≥ 48×48 px`.
   - Відображення та оновлення черги на KDS: до `75 активних замовлень` при `≥ 60 FPS` і затримці оновлення `p95 ≤ 300 мс`; звукове оповіщення про скасування — `≥ 70 дБ` тривалістю `3 с` із затримкою `p95 ≤ 500 мс`.
3. **Навантаження та поведінка понад межу (Overload behavior):**
   - **Штатне (очікуване):** `150 одночасних сесій`, `15 нових замовлень/хв` (~50 RPS).
   - **Пікове:** до `500 одночасних сесій`, до `50 нових замовлень/хв` (~200 RPS) із часом відгуку читання `p95 ≤ 250 мс` і запису `p95 ≤ 400 мс`.
   - **Понад межу (> 500 сесій або > 200 RPS):** спрацьовує Rate Limiter зі статусом `HTTP 429 Too Many Requests` та заголовком `Retry-After: 5` (запити оплати й кухні обробляються через пріоритетну чергу без втрати даних).
4. **Безпека, локалізація та технологічний стек:**
   - Шифрування трафіку `TLS 1.3`, делегування карткових платежів шлюзу `PCI DSS Level 1` (без збереження PAN/CVV у БД), `OAuth 2.0 / JWT` (`access TTL = 15 хв`, `refresh TTL = 7 діб`), `bcrypt (cost factor ≥ 12)`, блокування акаунту на `15 хв` після `5 невдалих спроб` входу, зберігання audit-логу `≥ 365 діб`.
   - Захист від овербукінгу: транзакції з рівнем ізоляції `SERIALIZABLE` / `SELECT ... FOR UPDATE` (таймаут `≤ 2 с`, `0%` колізій).
   - Мови: українська та англійська як основні (додатково DE, FR, ES), автовизначення за `Accept-Language`, перемикання за `p95 ≤ 100 мс`.
   - Стек: `React Native (TypeScript)` для мобільного застосунку та планшета офіціанта, `Vue 3 (TypeScript)` для вебпанелі адміністратора та KDS, `Python 3.12 + FastAPI`, `PostgreSQL 16`, `Redis 7`.

### 6.2. Виконання та інженерна аргументація прийнятих рішень

#### 1. Аргументація профілю вимірювання при 350 сесіях та структури каталогу страв (`requirements.md`, §6.1)
- **Чому обрано поріг у 350 одночасних сесій для профілю вимірювання SLA клієнта:**
  Штатне навантаження системи становить `150 сесій`, а абсолютний пік до відсікання трафіку — `500 сесій`. Точка у **`350 одночасних сесій`** (70% від максимальної ємності сервера, або режим високого вечірнього завантаження ресторану / п'ятничного прайм-тайму) є класичною інженерною точкою перевірки SLA (Sub-Peak Load Testing). Саме на 350 сесіях система вже працює під суттєвим конкурентним навантаженням на пул з'єднань PostgreSQL та кеш Redis, але ще не відхиляє запити через Rate Limiter (`HTTP 429`).
- **Як саме рахується розмір каталогу страв при вимірюванні `p95 ≤ 1.5 с`:**
  Якщо завантажувати 100 повнорозмірних фотографій страв одночасно (наприклад, по 1–2 МБ кожна), жодна мобільна мережа 4G не вкладеться в `1.5 с`. Тому в критерії зафіксовано реалістичну архітектурну модель:
  1. **Текстові метадані каталогу (до 100 позицій меню):** серіалізований JSON-пейлоад зі структурою категорій, назвами, цінами та статусом `is_available` має обсяг **до 150 КБ** (з кешуванням у Redis і стисненням Gzip/Brotli передається за `50–100 мс`).
  2. **Візуальний контент першого екрана (Above-the-Fold Rendering):** метрика первинного відмальовування враховує завантаження прев'ю-зображень (WebP/AVIF, стиснених **до 80 КБ кожне**) лише для перших **12 видимих карток страв** на екрані смартфона або вебсайту (сумарний трафік першого екрана `~1.1 МБ`, що при швидкості 4G 10–15 Мбіт/с гарантовано рендериться в межах `p95 ≤ 1.5 с`), тоді як решта зображень підвантажується ліниво (*lazy loading*) під час скролінгу.
- **Профіль для перерахунку вартості чека (`p95 ≤ 200 мс`):**
  Вимірюється також при **350 активних сесіях** для кошика, що містить **до 15 позицій**. Оскільки проміжний підрахунок виконується в пам'яті/кеші сесії без важких транзакційних блокувань таблиць, `200 мс` для `p95` є повністю досяжним показником.

#### 2. Аргументація розподілу клієнтських пристроїв та ОС (§6.1–6.4 та `spec.md`)
- **Клієнт / Гість (iOS, Android + Вебсайт):** додавання вебсайту поряд із мобільним застосунком є критично важливим для сценарію `Takeaway` та швидкого бронювання за QR-кодом на столі — відвідувачу не обов'язково встановлювати застосунок з App Store / Google Play, щоб зробити замовлення.
- **Офіціант (планшети iOS або стаціонарні POS-термінали):** у реальних закладах офіціанти приймають замовлення біля столу з планшета iPad, але закриття чека, друк фіскального рахунку або робота на роздачі часто виконуються зі стаціонарного сенсорного POS-термінала в залі.
- **Адміністратор (ПК/ноутбук на Windows ≥ 10, Linux, macOS):** управління картою залу, змінами та аналітикою виконується на робочому місці хостес/менеджера, де стандартом є десктопні ОС. Обмеження `Windows не молодше версії 10` зумовлене підтримкою сучасних стандартів безпеки браузерів (`TLS 1.3`, сучасний WebSocket API) та припиненням підтримки старіших версій ОС.
- **Кухар (сенсорні екрани з мінімумом кнопок + настінні телевізори):** на гарячій лінії кухні кухарі працюють у рукавичках або з вологими руками, тому для зміни статусу на «Готово» використовується спеціалізований сенсорний екран з великими кнопками (мінімум елементів керування), а для загального огляду черги всією бригадою кухарів використовуються великі настінні телевізори в режимі пасивного інформаційного табло (read-only).

#### 3. Поширення політики захисту від перевантаження (`HTTP 429 Too Many Requests`)
- Код `HTTP 429` додано не лише в загальносистемний розділ (§6.5 при перевищенні 500 сесій / 200 RPS), а й точково на рівні кожної ролі:
  - Для **клієнта (§6.1)** — захист від спаму запитами оновлення меню та багаторазового натискання кнопок зміни кошика.
  - Для **офіціанта (§6.2)** — захист каналу синхронізації статусів столів при масових одночасних оновленнях з терміналів.
  - Для **адміністратора (§6.3)** — захист адміністративних ендпоінтів від brute-force та перевантаження.
  - Для **кухні (§6.4)** — гарантія того, що при сплеску понад 75 активних замовлень та перевантаженні потоку оновлень (`HTTP 429`) інформаційний екран/телевізор кухаря зберігає поточний відмальований стан черги без аварійного скидання інтерфейсу.

#### 4. Узгодження `Pre-order` у `spec.md` (рядок 35) із ER-моделлю Lab1
- У попередній редакції `spec.md` у рядку 35 випадково з'явилося формулювання *«Pre-order без бронювання»*, яке прямо суперечило:
