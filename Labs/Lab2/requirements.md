## 1. EARS-вимоги

### 1.1. Управління посадкою та бронюванням

| ID | EARS |
| :--- | :--- |
| REQ1 | WHEN клієнт або адміністратор обирають дату, час, кількість гостей та столи для бронювання, the system TableFlow SHALL перевірити доступність обраних столів на вказаний інтервал часу |
| REQ2 | IF на запитуваний інтервал часу немає вільних місць, THEN the system TableFlow SHALL запропонувати альтернативні доступні столи або інший час візиту |
| REQ3 | IF кількість обраних столів для одного бронювання перевищує 3, THEN the system TableFlow SHALL заблокувати створення бронювання та відобразити помилку |
| REQ4 | WHEN користувач підтверджує бронювання доступних столів (від 1 до 3), the system TableFlow SHALL закріпити обрані столи та перевести їх у статус "Заброньовано" |
| REQ5 | WHEN клієнт або адміністратор скасовують або переносять бронювання, the system TableFlow SHALL зняти резервування зі столів та оновити їхній статус на "Вільний" |
| REQ6 | The system TableFlow SHALL відображати адміністратору інтерактивну карту залу з актуальними статусами всіх столів |
| REQ7 | WHEN адміністратор здійснює оперативну посадку гостей у порядку живої черги, the system TableFlow SHALL закріпити вільний стіл та встановити для нього статус "Зайнятий" |
| REQ8 | WHEN настає налаштований інтервал часу до початку заброньованого візиту, the system TableFlow SHALL надіслати клієнту нагадування з деталями броні через сервіс сповіщень Notification Service |


### 1.2. Оформлення та редагування замовлень

| ID | EARS |
| :--- | :--- |
| REQ9 | WHEN клієнт або офіціант підтверджують замовлення, the system TableFlow SHALL створити нове замовлення |
| REQ10 | WHERE клієнт здійснює попереднє бронювання столу, the system TableFlow SHALL надати можливість оформити попереднє замовлення страв |
| REQ11 | WHEN гість оформлює замовлення з собою, the system TableFlow SHALL зареєструвати замовлення на винос та згенерувати унікальний код видачі |
| REQ12 | The system TableFlow SHALL перераховувати та відображати користувачу проміжну вартість чека під час будь-яких змін у замовленні |
| REQ13 | WHILE замовлення перебуває в активному статусі (до передачі на кухню або початку готування), the system TableFlow SHALL дозволяти редагувати перелік та кількість страв |
| REQ14 | IF замовлення вже передано на кухню або перебуває в процесі приготування, THEN the system TableFlow SHALL заблокувати редагування замовлення |
| REQ15 | IF обрана страва закінчилася, THEN the system TableFlow SHALL заблокувати її додавання до замовлення |


### 1.3. Підсистема оплати

| ID | EARS |
| :--- | :--- |
| REQ16 | WHEN клієнт натискає "Оплатити", the system TableFlow SHALL надати доступні методи розрахунку: онлайн-оплата (Apple Pay / Google Pay / картка), оплата офіціанту в залі або подарунковим сертифікатом |
| REQ17 | WHEN клієнт або гість обирає онлайн-оплату, the system TableFlow SHALL передати платіжний запит до платіжного шлюзу та після успішної транзакції перевести замовлення у статус "Сплачено" |
| REQ18 | IF платіжний шлюз відхиляє транзакцію, THEN the system TableFlow SHALL сповістити користувача про збій платежу та залишити рахунок відкритим для повторної спроби або вибору іншого способу розрахунку |
| REQ19 | WHEN офіціант проводить розрахунок клієнтів у залі готівкою або через термінал, the system TableFlow SHALL зафіксувати оплату замовлення та перевести стіл у статус "Вільний" |
| REQ20 | WHEN гість надає цифровий код замовлення з собою для оплати готівкою в закладі, the system TableFlow SHALL верифікувати код, зафіксувати оплату та дозволити видачу замовлення |
| REQ21 | WHERE клієнт або гість застосовує подарунковий сертифікат, the system TableFlow SHALL зменшити кінцеву суму чека на номінал сертифіката з можливістю доплати залишку іншим доступним способом |


### 1.4. Комунікація між залом та кухнею

| ID | EARS |
| :--- | :--- |
| REQ22 | WHEN замовлення підтверджено клієнтом або офіціантом, the system TableFlow SHALL додати його до черги замовлень кухарю |
| REQ23 | The system TableFlow SHALL відображати кухарю чергу активних замовлень із сортуванням за часом надходження та зазначенням номера столу і закріпленого офіціанта |
| REQ24 | WHEN кухар змінює статус замовлення на "Готово", the system TableFlow SHALL надіслати сповіщення закріпленому офіціанту або гостю через сервіс повідомлень `Notification Service` |
| REQ25 | WHEN кухар додає позицію меню до стоп-листа, the system TableFlow SHALL заблокувати страву для формування нових замовлень |
| REQ26 | IF замовлення скасовується або змінюється після передачі на кухню, THEN the system TableFlow SHALL надіслати сповіщення кухарю на кухонний дисплей про зупинку приготування |
| REQ27 | The system TableFlow SHALL формувати та відображати кухарю та адміністратору зведену денну статистику щодо кількості виконаних замовлень і середнього часу приготування страв |


## 2. User Stories

### 2.1. Управління посадкою та бронюванням

| ID | Роль / Актор | Бажання | Мета |
| :--- | :--- | :--- | :--- |
| US1.1 | Клієнт | Самостійно обирати дату, час, кількість гостей і бронювати до 3 столів через мобільний застосунок | Гарантовано забезпечити посадочні місця для своєї компанії до приходу в ресторан |
| US1.2 | Адміністратор | Переглядати кількість і статуси столів на інтерактивній карті залу в реальному часі та оперативно саджати гостей без броні | Швидко розміщувати відвідувачів у порядку живої черги та мінімізувати час простою залу |
| US1.3 | Клієнт або Адміністратор | Скасовувати або переносити бронь столу до настання заброньованого часу | Своєчасно звільнити столи для інших гостей або скоригувати час візиту без штрафів |
| US1.4 | Клієнт | Отримувати завчасні нагадування з деталями броні за обраний період до початку візиту | Не забути про запланований візит |


### 2.2. Оформлення та редагування замовлень

| ID | Роль / Актор | Бажання | Мета |
| :--- | :--- | :--- | :--- |
| US2.1 | Клієнт | Самостійно переглядати електронне меню, додавати страви та формувати замовлення в застосунку | Зручно замовляти їжу та не витрачати час на очікування офіціанта в залі |
| US2.2 | Клієнт | Бачити актуальну проміжну суму замовлення в застосунку під час будь-яких змін у кошику | Самостійно контролювати свій бюджет і чек до моменту підтвердження замовлення |
| US2.3 | Клієнт та Офіціант | Редагувати склад замовлення (включаючи можливість вказати інгредієнти, які необхідно вилучити) до переходу замовлення в статус «У приготуванні» | Отримати страви відповідно до своїх індивідуальних смаків або дієтичних вимог |
| US2.4 | Клієнт | Оформити попереднє замовлення страв після бронювання столу та підтвердити його перед початком приготування | Отримати готові свіжі страви точно до свого прибуття і не чекати їх у закладі |
| US2.5 | Гість | Швидко оформлювати замовлення страв "із собою" без обов'язкової реєстрації та бачити шкалу очікування і статус приготування | Максимально заощадити час і зручно забрати готове замовлення |
| US2.6 | Офіціант | Вносити та підтверджувати замовлення гостей безпосередньо біля столу з власного робочого планшета | Точно зафіксувати усні прохання клієнтів і миттєво передати їх на кухню |


### 2.3. Підсистема оплати

| ID | Роль / Актор | Бажання | Мета |
| :--- | :--- | :--- | :--- |
| US3.1 | Клієнт | Оплачувати рахунок онлайн через зручні платіжні сервіси (Apple Pay / Google Pay / банківська картка) | Здійснювати швидкий, безпечний і безконтактний розрахунок прямо в застосунку |
| US3.2 | Офіціант | Приймати оплату від гостей за столом готівкою або банківською карткою через мобільний POS-термінал | Забезпечити гостям традиційні способи розрахунку та своєчасно закривати рахунки столів |
| US3.3 | Гість | Оплачувати замовлення онлайн або отримувати унікальний цифровий код для оплати готівкою в пункті видачі ресторану | Забрати замовлену їжу без затримок у найбільш зручний спосіб оплати |
| US3.4 | Клієнт або Гість | Частково або повністю оплачувати замовлення подарунковим сертифікатом у застосунку чи на касі закладу | Вигідно використати подарований баланс і за потреби доплатити залишок іншим способом |
| US3.5 | Клієнт | Зберігати електронні чеки та повну історію замовлень у застосунку незалежно від способу оплати | Мати офіційне підтвердження транзакцій і зручний доступ до історії власних витрат |


### 2.4. Комунікація між залом та кухнею

| ID | Роль / Актор | Бажання | Мета |
| :--- | :--- | :--- | :--- |
| US4.1 | Кухар | Бачити чергу активних замовлень на кухонному дисплеї з особливими побажаннями клієнтів та автоматичною пріоритизацією | Своєчасно та в оптимальній черговості готувати й віддавати страви відвідувачам |
| US4.2 | Кухар | Миттєво отримувати сповіщення про будь-які підтверджені зміни або скасування замовлення до початку його приготування | Уникнути псування продуктів і не готувати страви, які клієнт скасував або змінив |
| US4.3 | Кухар | В один клік додавати відсутні страви чи закінчені інгредієнти до стоп-листа кухні | Автоматично блокувати в меню позиції, які кухня наразі не в змозі приготувати |
| US4.4 | Офіціант або Гiсть | Отримувати оперативне сповіщення, як тільки страва переходить у статус "Готово" (з можливістю налаштувати фільтрацію сповіщень) | Негайно забрати страву з роздачі та подати її гостям максимально свіжою та гарячою |
| US4.5 | Кухар або Адміністратор | Наприкінці робочого дня переглядати зведену статистику щодо кількості обслугованих замовлень і середнього часу їх приготування | Об'єктивно оцінювати продуктивність кухні та оптимізувати операційні процеси закладу |
