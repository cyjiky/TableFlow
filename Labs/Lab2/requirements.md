## 1. EARS-вимоги

### 1.1. Управління посадкою та бронюванням

| ID | EARS |
| :--- | :--- |
| REQ1 | WHEN клієнт або адміністратор обирають дату, час, кількість гостей та столи для бронювання, the system TableFlow SHALL перевірити доступність обраних столів на вказаний інтервал часу |
| REQ2 | IF на запитуваний інтервал часу немає вільних місць, THEN the system TableFlow SHALL запропонувати альтернативні доступні столи або інший час візиту |
| REQ3 | IF кількість обраних столів для одного бронювання перевищує 3, THEN the system TableFlow SHALL заблокувати створення бронювання та відобразити помилку |
| REQ4 | WHEN користувач підтверджує бронювання доступних столів (від 1 до 3), the system TableFlow SHALL закріпити обрані столи та перевести їх у статус "Заброньовано" |
| REQ5 | WHEN клієнт або адміністратор скасовують або переносять бронювання, the system TableFlow SHALL зняти резервування зі столів та оновити їхній статус на "Вільний" |
| REQ6 | The system TableFlow SHALL відображати адміністратору інтерактивну карту залу з актуальними статусами всіх столів |
| REQ7 | WHEN адміністратор здійснює оперативну посадку гостей у порядку живої черги, the system TableFlow SHALL закріпити вільний стіл та встановити для нього статус "Зайнятий" |


### 1.2. Оформлення та редагування замовлень

| ID | EARS |
| :--- | :--- |
| REQ8 | WHEN клієнт або офіціант підтверджують замовлення, the system TableFlow SHALL створити нове замовлення |
| REQ9 | WHERE клієнт здійснює попереднє бронювання столу, the system TableFlow SHALL надати можливість оформити попереднє замовлення страв |
| REQ10 | WHEN гість оформлює замовлення з собою, the system TableFlow SHALL зареєструвати замовлення на винос та згенерувати унікальний цифровий код видачі |
| REQ11 | The system TableFlow SHALL перераховувати та відображати користувачу проміжну вартість чека під час будь-яких змін у замовленні |
| REQ12 | WHILE замовлення перебуває в активному статусі (до передачі на кухню), the system TableFlow SHALL дозволяти клієнту самостійно редагувати перелік та кількість страв |
| REQ13 | IF замовлення вже передано на кухню або перебуває в процесі приготування, THEN the system TableFlow SHALL заблокувати самостійне редагування замовлення клієнтом |
| REQ14 | IF обрана страва закінчилася, THEN the system TableFlow SHALL заблокувати її додавання до замовлення |


### 1.3. Підсистема оплати

| ID | EARS |
| :--- | :--- |
| REQ15 | WHEN клієнт натискає "Оплатити", the system TableFlow SHALL надати доступні методи розрахунку: онлайн-оплата (Apple Pay / Google Pay / картка), оплата офіціанту в залі або подарунковим сертифікатом |
| REQ16 | WHEN клієнт обирає онлайн-оплату, the system TableFlow SHALL передати платіжний запит до платіжного шлюзу та після успішної транзакції перевести замовлення у статус "Сплачено" |
| REQ17 | IF платіжний шлюз відхиляє транзакцію, THEN the system TableFlow SHALL сповістити користувача про збій платежу та залишити рахунок відкритим для повторної спроби або вибору іншого способу розрахунку |
| REQ18 | WHEN офіціант проводить розрахунок клієнтів у залі готівкою або через термінал, the system TableFlow SHALL зафіксувати оплату замовлення та перевести стіл у статус "Вільний" |
| REQ19 | WHEN гість надає цифровий код замовлення з собою для оплати готівкою в закладі, the system TableFlow SHALL верифікувати код, зафіксувати оплату та дозволити видачу замовлення |
| REQ20 | WHERE клієнт або гість застосовує подарунковий сертифікат, the system TableFlow SHALL зменшити кінцеву суму чека на номінал сертифіката з можливістю доплати залишку іншим доступним способом |


### 1.4. Комунікація між залом та кухнею

| ID | EARS |
| :--- | :--- |
| REQ21 | WHEN замовлення підтверджено клієнтом або офіціантом, the system TableFlow SHALL додати його до черги замовлень кухарю |
| REQ22 | The system TableFlow SHALL відображати кухарю чергу активних замовлень із сортуванням за часом надходження та зазначенням номера столу і закріпленого офіціанта |
| REQ23 | WHEN кухар змінює статус замовлення на "Готово", the system TableFlow SHALL надіслати сповіщення закріпленому офіціанту через сервіс повідомлень `Notification Service` |
| REQ24 | WHEN кухар додає позицію меню до стоп-листа, the system TableFlow SHALL заблокувати страву для формування нових замовлень |
| REQ25 | IF замовлення скасовується або змінюється після передачі на кухню, THEN the system TableFlow SHALL надіслати сповіщення кухарю на кухонний дисплей про зупинку приготування |


## 2. User Stories

### 2.1. Управління посадкою та бронюванням

| ID | Роль / Актор | Бажання | Мета |
| :--- | :--- | :--- | :--- |
| US1.1 | Клієнт | Самостійно обирати дату, час, кількість гостей і бронювати до 3 столів через мобільний застосунок | Гарантовано забезпечити посадочні місця для своєї компанії до приходу в ресторан |
| US1.2 | Адміністратор | Переглядати кількість і статуси столів на інтерактивній карті залу в реальному часі та оперативно саджати гостей без броні | Швидко розміщувати відвідувачів у порядку живої черги та мінімізувати час простою залу |
| US1.3 | Клієнт або Адміністратор | Скасовувати або переносити бронь столу до настання заброньованого часу | Своєчасно звільнити столи для інших гостей або скоригувати час візиту без штрафів |
| US1.4 | Клієнт | Отримувати завчасні нагадування з деталями броні за обраний період до початку візиту | Не забути про запланований візит |


### 2.2. Оформлення та редагування замовлень

| ID | Роль / Актор | Бажання | Мета |
| :--- | :--- | :--- | :--- |
| US2.1 | Клієнт | Самостійно переглядати електронне меню, додавати страви та формувати замовлення в застосунку | Зручно замовляти їжу та не витрачати час на очікування офіціанта в залі |
| US2.2 | Клієнт | Бачити актуальну проміжну суму замовлення в застосунку під час будь-яких змін у кошику | Самостійно контролювати свій бюджет і чек до моменту підтвердження замовлення |
| US2.3 | Клієнт | Редагувати склад замовлення (включаючи можливість вказати інгредієнти, які необхідно вилучити) до переходу замовлення в статус «У приготуванні» | Отримати страви відповідно до своїх індивідуальних смаків або дієтичних вимог |
| US2.4 | Клієнт | Оформити попереднє замовлення страв (Pre-order) після бронювання столу та підтвердити його перед початком приготування | Отримати готові свіжі страви точно до свого прибуття і не чекати їх у закладі |
| US2.5 | Гість | Швидко оформлювати замовлення страв «із собою» (Takeaway) без обов'язкової реєстрації та бачити шкалу очікування і статус приготування | Максимально заощадити час і зручно забрати готове замовлення |
| US2.6 | Офіціант | Вносити та підтверджувати замовлення гостей безпосередньо біля столу з власного робочого планшета | Точно зафіксувати усні прохання клієнтів і миттєво передати їх на кухню |


### 2.3. Підсистема оплати

| ID | Роль / Актор | Бажання | Мета |
| :--- | :--- | :--- | :--- |
| US3.1 | Клієнт | Оплачувати рахунок онлайн через зручні платіжні сервіси (Apple Pay / Google Pay / банківська картка) | Здійснювати швидкий, безпечний і безконтактний розрахунок прямо в застосунку |
| US3.2 | Офіціант | Приймати оплату від гостей за столом готівкою або банківською карткою через мобільний POS-термінал | Забезпечити гостям традиційні способи розрахунку та своєчасно закривати рахунки столів |
| US3.3 | Гість | Оплачувати замовлення онлайн або отримувати унікальний цифровий код для оплати готівкою в пункті видачі ресторану | Забрати замовлену їжу без затримок у найбільш зручний спосіб оплати |
| US3.4 | Клієнт або Гість | Частково або повністю оплачувати замовлення подарунковим сертифікатом у застосунку чи на касі закладу | Вигідно використати подарований баланс і за потреби доплатити залишок іншим способом |
| US3.5 | Клієнт | Зберігати електронні фіскальні чеки та повну історію замовлень у застосунку незалежно від способу оплати | Мати офіційне підтвердження транзакцій і зручний доступ до історії власних витрат |


### 2.4. Комунікація між залом та кухнею

| ID | Роль / Актор | Бажання | Мета |
| :--- | :--- | :--- | :--- |
| US4.1 | Кухар | Бачити чергу активних замовлень на кухонному дисплеї з особливими побажаннями клієнтів та автоматичною пріоритизацією | Своєчасно та в оптимальній черговості готувати й віддавати страви відвідувачам |
| US4.2 | Кухар | Миттєво отримувати сповіщення про будь-які підтверджені зміни або скасування замовлення до початку його приготування | Уникнути псування продуктів і не готувати страви, які клієнт скасував або змінив |
| US4.3 | Кухар | В один клік додавати відсутні страви чи закінчені інгредієнти до стоп-листа кухні | Автоматично блокувати в меню позиції, які кухня наразі не в змозі приготувати |
| US4.4 | Офіціант або Клієнт | Отримувати оперативне сповіщення, як тільки страва переходить у статус «Готово» (з можливістю налаштувати фільтрацію сповіщень) | Негайно забрати страву з роздачі та подати її гостям максимально свіжою та гарячою |
| US4.5 | Кухар або Адміністратор | Наприкінці робочого дня переглядати зведену статистику щодо кількості обслугованих замовлень і середнього часу їх приготування | Об'єктивно оцінювати продуктивність кухні та оптимізувати операційні процеси закладу |


## 3. Gherkin

### 3.1. Управління посадкою та бронюванням

```gherkin
Feature: Управління посадкою та бронюванням столів
  Як зареєстрований клієнт або адміністратор ресторану
  Я хочу бронювати столи та керувати посадкою відвідувачів
  Щоб гарантувати наявність вільних місць та організувати комфортне розміщення гостей

  Background:
    Given користувач зареєстрований у системі з роллю "CLIENT"

  Scenario: Автоматичний вибір вільного столу системою при бронюванні
    When клієнт оформлює бронювання на дату, час, кiлькiсть гостей без вибору конкретного столу
      And підтверджує створення бронювання
    Then система бронює будь-який підходящий вільний стіл на цей час
      And статус обраного столу переходить у "Заброньовано" на вказаний інтервал
      And клієнт отримує підтвердження успішного бронювання в застосунку

  Scenario: Ручний вибір конкретного столу клієнтом
    Given стіл <номер> має статус "Вільний" на обрану дату i час
    When клієнт обирає дату, час, кiлькiсть гостей та стіл №4 зі списку доступних
      And підтверджує створення бронювання
    Then система бронює саме стіл <номер> на цей інтервал часу
      And статус столу <номер> переходить у стан "Заброньовано"
      And клієнт отримує підтвердження успішного бронювання

  Scenario: Відсутність вільних столів у залі на обраний час
    Given усі столи в залі зайняті або заброньовані
    When клієнт обирає дату та час для бронювання
    Then система сповіщає клієнта в застосунку про відсутність вільних столів
      And система пропонує інші доступні варіанти дат або інтервалів часу

  Scenario: Відхилення бронювання при перевищенні ліміту в 3 столи
    When клієнт намагається обрати 4 столи в межах одного бронювання
    Then система блокує створення бронювання
    And відображає повідомлення про помилку: "Максимальна кількість столів для одного бронювання: 3"

  Scenario: Скасування бронювання клієнтом
    Given клієнт має активне бронювання зі закріпленим столом <номер>
    When клієнт скасовує це бронювання до початку заброньованого часу
    Then система переводить стіл <номер> у статус "Вільний" на цей період
    And система надсилає повідомлення клієнту про успішне скасування бронювання

  Scenario: Посадка гостей за живою чергою адміністратором
    Given адміністратор "ADMIN" переглядає інтерактивну карту залу в реальному часі
      And стіл <номер> має статус "Вільний"
    When до закладу прибуває компанія гостей без попередньої броні
      And адміністратор закріплює за ними стіл <номер> на карті залу
    Then система негайно переводить статус столу <номер> у стан "Зайнятий"
    And інтерактивна карта залу миттєво відображає стіл <номер> зайнятим
```

### 3.2. Оформлення та редагування замовлень

```gherkin
Feature: Оформлення та редагування замовлень
  Як відвідувач або офіціант закладу
  Я хочу формувати та редагувати замовлення страв
  Щоб отримати бажані позиції меню та контролювати вартість чека

  Scenario: Самостійне замовлення клієнтом у залі з підрахунком проміжної ціни
    Given клієнт авторизований за столом <номер> із новою сесією замовлення
    When клієнт додає до замовлення страву
    Then система відображає актуальну проміжну вартість
    When клієнт підтверджує оформлення замовлення
    Then замовлення створюється зі статусом "ACTIVE"
      And замовлення автоматично відображається в черзі на кухонному дисплеї
      And на екрані клієнта відображається орієнтовний час очікування та статус приготування

  Scenario: Оформлення та підтвердження замовлення офіціантом біля столу
    Given офіціант відкриває замовлення для столу <номер>
    When офіціант додає до замовлення обрані гостями позиції
      And підтверджує замовлення зі свого планшета
    Then замовлення створюється зі статусом "ACTIVE"
      And деталі замовлення надходять на кухню для початку приготування

  Scenario: Швидке оформлення замовлення "З собою" неавторизованим гостем
    Given неавторизований відвідувач відкриває застосунок у режимі "GUEST"
    When гість додає до кошика страви у режимі замовлення з собою
      And підтверджує замовлення без проходження авторизації
    Then система реєструє замовлення типу "З собою" без прив'язки до столу
      And система генерує унікальний цифровий код видачі
      And на екрані гостя відображається шкала очікування та статус приготування

  Scenario: Заборона редагування замовлення після передачі кухарю
    Given замовлення клієнта перейшло у статус "COOKING" на кухні
    When клієнт намагається змінити або видалити страву через застосунок
    Then система блокує спробу самостійного редагування
      And відображає сповіщення: "Замовлення вже готується, зміни недоступні"
```

### 3.3. Підсистема оплати

```gherkin
Feature: Підсистема оплати рахунків
  Як відвідувач або персонал ресторану
  Я хочу проводити розрахунок різними зручними методами
  Щоб забезпечити коректне закриття рахунку, безпеку платежу та фіскалізацію

  Background:
    Given клієнт має відкрите неоплачене замовлення в системі

  Scenario: Онлайн-оплата замовлення через Apple Pay
    When клієнт обирає спосіб онлайн-оплати "Apple Pay"
      And підтверджує платіж у системі
      And платіжний шлюз повертає підтвердження успішної транзакції
    Then замовлення переводиться у статус "Сплачено"
      And система генерує електронний фіскальний чек в історії замовлень клієнта

  Scenario: Оплата замовлення офіціанту готівкою або через POS-термінал
    Given офіціант відкриває рахунок замовлення <номер>
    When гості розраховуються готівкою або банківською карткою через платіжний термінал
    And офіціант підтверджує оплату в застосунку
    Then система фіксує оплату замовлення <номер>
    And стіл <номер> переходить у статус "Вільний" на карті залу

  Scenario: Оплата замовлення «Takeaway» готівкою за цифровим кодом у закладі
    Given гість має замовлення з собою зі згенерованим цифровим кодом "482910"
    When гість надає код "482910" касиру в пункті видачі та сплачує суму замовлення готівкою
    And касир підтверджує валідність коду в системі
    Then система переводить замовлення в статус "Сплачено"
    And дозволяє видачу упакованого замовлення гостю

  Scenario Outline: Оплата замовлення подарунковим сертифікатом із доплатою залишку
    When користувач застосовує подарунковий сертифікат номіналом <cert_value>
    Then сума чека зменшується на <cert_value>
      And залишок суми повинен бути доплачений будь-яким методом

    Examples:
      | order_sum |
      | 10        |
      | 50        |
      | 100       |
```

### 3.4. Комунікація між залом та кухнею

```gherkin
Feature: Комунікація між залом та кухнею
  Як кухар або офіціант закладу
  Я хочу отримувати оперативні сповіщення та актуальну інформацію щодо замовлень
  Щоб оптимізувати процес приготування та своєчасно видавати свіжі страви гостям

  Scenario: Відображення нового замовлення з особливими побажаннями на кухні
    Given клієнт підтвердив замовлення
      And вказав особливе побажання
    When замовлення фіксується системою
    Then воно миттєво з'являється в черзі на кухонному моніторі кухаря
      And картка замовлення містить номер замовлення та перелік страв

  Scenario: Сповіщення офіціанта про готовність замовленої страви
    Given кухар приготував страву для замовлення <номер>
    When кухар позначає страву статусом "Готово"
    Then система ініціює відправку сповіщення через сервіс Notification Service
      And офіціант, закріплений за цим замовленням, отримує повідомлення про готовність страви до видачі

  Scenario: Блокування замовлення страви після внесення її до стоп-листа
    Given на кухні закінчилися інгредієнти для страви <назва>
    When кухар додає страву <назва> до стоп-листа кухні
    Then ця страва негайно стає недоступною для вибору в електронному меню застосунку
      And жоден користувач не може додати цю страву до нового замовлення
```
